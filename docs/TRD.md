# Trinqle: Technical Requirements (v1)

Read PRD.md first. This document says *how*. Stack choices are defaults; equivalents are fine if constraints below hold.

## 1. Stack
- **TypeScript + React + Vite**, `vite-plugin-pwa` (Workbox, `injectManifest` so a custom push handler is possible).
- **Dexie** (IndexedDB) behind a **repository layer** (UI never touches Dexie directly, so storage is swappable/syncable later).
- State: Zustand (UI state only; data comes from repositories + live queries).
- Charts: hand-rolled SVG with `d3-scale`/`d3-shape` (small, themeable, easy to freeze as models).
- Stats: small in-house functions (+ `simple-statistics` allowed). Analysis runs in a **Web Worker**.
- Icons: `lucide-react` behind each theme's iconSet (semantic keys, no emojis). Zip: `fflate` or `jszip`. SVG sanitising: `DOMPurify` (SVG profile). IDs: UUIDv7.
- Tests: Vitest (unit, property), Playwright (e2e, mobile viewport). Hosting: Vercel. Push server: Vercel serverless functions + Upstash/Vercel KV.

## 2. Repository layout
```
src/
  core/        pure TS, no DOM, no Dexie: logicalDay, formEngine, metrics, stats, engine/, freeze, packs, ids
  data/        Dexie schema, repositories, migrations, import/export
  ui/          screens (home, dashboard, insights, archive, profile, editor), widgets, charts
  themes/      one file per theme + registry
  characters/  svg + character.json + animator
  sw/          service worker (precache, push)
api/           subscribe.ts, unsubscribe.ts, prefs.ts, send.ts (scheduler target)
tools/         demo-data generator, planted-effect validators
```
Rule: `core/` is testable in Node and reused by the Web Worker.
Repo root also holds `docs/` (PRD, TRD, design, v2-plan), `public/icons/logo.svg` (icon source; PNGs generated by assets-generator), `src/characters/`, `src/assets/stickers/`, `src/content/` (starter-form-pack.json, analytic-form-pack.json, greetings.json) and `AGENTS.md`.

## 3. Data model
All records: `{ id: UUID, createdAt, updatedAt, deletedAt? }` (soft delete for sync-readiness). Dates are `YYYY-MM-DD` strings (logical dates); instants are epoch ms.

```ts
Section   { name, icon, order, scope:'daily'|'weekly'|'chapterEnd', validFrom?, validTo? }
Question  { sectionId, parentId?, label, icon?, order, repeats:boolean,
            special?:'cycle', showWhen?:Rule, schedule?:{weekdays?:number[], chapterEnd?:boolean},
            validFrom?, validTo? }
Part      { questionId, kind:'yesno'|'scale'|'number'|'text'|'timerange'|'library',
            label, order, level:'core'|'extra', gate?:boolean, config:PartConfig,
            validFrom?, validTo? }
  // config: scale {min,max,step,display:'stars'|'slider'} number {unit,min?,max?,step,aggregate:'sum'|'mean' (default sum)}
  //         text {multiline} timerange {snapMinutes} library {libraryId,multi,creatable}
Library   { name, retired? }
Item      { libraryId, name, retired?, mergedInto? }
Day       { date(PK), chapterId, title?, oneliner?, stickerId?, overallRating?, memorability:0|1|2|3,
            mode:'quick'|'full', expandedMore:boolean, backfilled:boolean, filledAt, editedAt?, tz }
Answer    { date, questionId, partId, instance:number, value:JSON }   // unique(date,partId,instance)
  // value: boolean | number | string | {start:'HH:mm',end:'HH:mm',crossesMidnight} | ID[] (item ids)
AnswerLink{ answerId, date, libraryId, itemId }       // denormalised index for library queries
Cycle     { startDate, endDate? }
ChapterAnswer { chapterId, promptId, value, updatedAt }   // promptId = a chapterEnd Part id or a customPrompt id; chapter-level, autosaved all chapter
Chapter   { title?, summary?, startDate, plannedEndDate, endDate?, status:'open'|'closed',
            themeId, characterId, customPrompts?:{id,label,type:'text'|'scale'}[], photos?:Blob[<=10], frozen?:FrozenChapter, closedAt? }
Baseline  { metricKey, weekdayMean[7], weekdaySd[7], n, asOfChapterId }
Run       { at, trigger:'sunday'|'manual', windowLabel, windowStart, windowEnd, nGenerated, nAboveBar, bar }
Insight   { runId, signature, windows, payload(facts+evidence days), sureness, surprise, score,
            rating?:1|2|3|4|5, status:'active'|'discarded' }
Sticker   { name, mime, blob, builtin }   // 12 built-ins in assets/stickers; imports sanitised/downscaled
Setting   { key, value }  // window hours, timeFormat ('12h' default), weekStart (1 = Monday default), theme, notification prefs, bar=6.5, minShow=20
```
Notes:
- `showWhen` Rule: `{ partId, op:'eq'|'truthy'|'in', value? } | { cycleActive:true }`.
- A `yesno` with `gate:true` hides sibling parts until true. Sub-questions inherit the parent's `instance`.
- Questions with `repeats:true`: every non-gate part is per-instance; the gate sits at instance 0.
- Library-valued answers write `AnswerLink` rows in the same transaction.
- `icon` fields hold semantic icon keys (e.g. `book-open`) resolved by the active theme's iconSet. No emojis anywhere. Weekday numbers in data use 0 = Sunday ... 6 = Saturday; `weekStart` only affects display and grouping.
- Every Question and Part has a required non-empty `label`. `config.display` (stars/slider) is presentation only; stored values are always numbers, so changing display never changes data.
- Chapter frozen data is stored on the Chapter row; day/answer rows stay in the live tables (needed for cross-chapter analysis) but are **write-protected** by the repository once their chapter is closed.

## 4. Logical day and time
`logicalDate(now, tz, windowEndHour)`: if local hour < windowEndHour then previous calendar date. `Day.tz` stores the IANA zone at save time; never recompute from the current zone. Window open when local time >= windowStart OR < windowEnd. Backfill allowed for `today-3 .. today-1` inside the open chapter only. Time ranges are stored as `HH:mm` plus `crossesMidnight`; minutes computed from them.

**Chapter lifecycle:** a chapter ends on its `plannedEndDate` (20 to 45 days from start, adjustable on Home). That night's form stays open until `windowEnd` the next morning. From the first app open when the logical date is after `endDate`, a **hard lock** (`ChapterGate`) replaces every route with the **Close Chapter** flow; nothing else is usable until it is completed. On T-2 and T-1 (and the end day) the Home countdown expands into a thick, dismissible pre-close pop-up. Flow steps: review reflections (+ custom prompts), title, summary, photos (0 to 10), confirm. Only confirming is mandatory (blank title becomes "Chapter N"). Confirming computes `FrozenChapter`, sets `status:'closed'` and creates the next chapter starting the day after `endDate`; days between `endDate` and the close are simply missing. Closed chapters are fully read-only, metadata included. Dev tools can set a simulated "today" to test the gate. Reflection answers live in `ChapterAnswer` (autosaved all chapter); custom prompts live on the `Chapter` row only.

## 5. Form engine (`core/formEngine`)
Pure functions over a form snapshot: `visibleQuestions(form, date, mode, answers, cycleState)`, `validate`, `isComplete(form, date, answers)`.
- **Completeness (required to save):** every reachable `core` part active on `date` must have a value; core `yesno` parts start blank (`undefined`, requiring explicit Yes or No); core parts under a `gate` or nested sub-question are required only when their parent gate is true; a repeating question with a true gate needs at least one session with all its core parts filled. Untouched extras are stored as absent (missing). A day is saved only when complete; incomplete drafts persist as drafts but create no Day row, so they count as unfilled (empty on the heatmap, no fill streak).
**Quick mode** shows questions that have at least one core part, and only their core parts, plus an inline "More questions" expander. The editor keeps a question's gate `core` if any sibling part is core.
**Effective-dating:** an item is active on `date` iff `validFrom <= date < validTo` (null = open); completeness of a past date is judged against the form effective on that date. Light edits (labels, order, icons, display, library items) mutate in place. Structural edits take a scope: *next chapter* sets `validFrom`/`validTo` to the next chapter's start; *this chapter* sets additions' `validFrom` to the current chapter's start and removals/core-extra changes to tomorrow. A kind change = new Part + retire old.

## 6. Metrics registry (`core/metrics`)
Each part kind declares metrics, all producing **daily numbers or missing**:
- yesno: `done`(0/1), plus derived `streak`.
- scale: `value` (mean over instances). number: `value` (**sum** over instances by default, e.g. steps or questions solved across sessions; `config.aggregate:'mean'` available).
- timerange: `minutes`(sum), `sessions`, `hourBins[24]` (sessions split across hours, wrap midnight), `startHour`.
- text: `written` (1 if non-empty; 0 if the part was shown that day and left blank; **missing** if it wasn't shown, i.e. not active, or a quick-mode extra when `expandedMore` is false), `words`, and the full-text index.
- library: `count`, and `item:<id>` presence (for items with >= 3 occurrences).
- Derived: sleep total/main, cycle day, weekday, days-since-X, memorability, overall rating.
Metric key = `${questionId}.${partId}.${metric}`. The **daily table** builder outputs rows per date with columns = active metrics + context. A metric is *missing* on dates outside its validity and for untouched extras. Dashboard graphs and insights are both driven only by this registry; no code mentions a specific question. The registry must stay extensible with **external metric sources** (to-do stats, imported numbers) that produce the same daily-number shape; not built in v1.

## 7. Insights engine (`core/engine`)
Pure, deterministic (seeded), runs in a Worker, budget ~10 s and a cap of about 50k candidate tests; returns partial results with `truncated:true` if hit.

**Candidates**
1. Driver to outcome pairs at lags 0..3 (drivers: yesno/minutes/counts/library-item presence, text `written`; outcomes: scales, numbers, sleep, memorability, ratings).
2. Test by pair type: binary vs numeric: Mann-Whitney U (+ Cliff's delta) or Welch t; numeric vs numeric: Spearman. Detrend weekday (subtract weekday means) when n >= 5 per weekday; otherwise flag weekday confounding.
3. Library lag: observed co-occurrence of item A at day d and item B at d+k vs permutation null (shuffle within chapter/weekday).
4. Anomalies: robust z (median/MAD) vs rolling baseline and chapter baselines; change points via CUSUM/binary segmentation; rough/best stretches; streak records.
5. Cycle-phase effects (outcome by phase).
6. Simple conditions: depth <= 2 rules (e.g. sleep < 6 h AND no exercise to mood) via greedy rule search with min support; v1 caps at 3-way.
7. "Best days had in common": compare top-quartile days vs rest across all drivers.

**Numbers and text:** all metrics are compared with rank-based or standardised statistics, so scale and unit never matter (steps in the thousands vs mood out of 10 vs glasses of water). A number's 0 is a real value; empty is missing. Phrasing uses `config.unit` and the user's own percentiles. Text parts take part only through `written` (and `words`).

**Multiple testing:** Benjamini-Hochberg across all tests in a run, min effective n per test (n_min configurable, default 5 so day-one runs produce weird output). Never drop low-n results; reflect them in sureness.

**Scoring**
- `sureness` 0..10 = f(1 - q-value, n, effect stability); tiny n caps it (<1 for n<8 by construction).
- `surprise` 0..10 = f(|effect| vs the metric's own spread and baseline, novelty vs previous runs, user's low prior if library-based).
- `score = sqrt(sureness * surprise)`.
- Display: all with `score >= bar (6.5)`, padded to `minShow (20)` by next best; header shows `nAboveBar`.
- Dedupe by `signature` = hash(sorted metric keys, lag, window kind, direction). Known signatures marked "still true"; discarded signatures suppressed.

**Phrasing:** compose sentences from facts (subject metric, comparison, magnitude in the user's units, n, rank vs own days) with plain-language converters (minutes to "1h 20m", effect to "1.2 points higher on a 10-point scale", percentile to "higher than 94% of your days"). No per-insight-type fixed templates. Casual/blunt tone. Always attach evidence days (titles + one-liners).

**Windows:** week, 4 weeks, current chapter, last 3 chapters, all-time vs `Baseline`. After each chapter close, update `Baseline` (recency-weighted, per weekday).

## 8. Freezing a chapter (`core/freeze`)
On close, compute and store `FrozenChapter`: `formSnapshot` (items active during the chapter), `dashboard` (render-agnostic **chart models**: type, series, axes, labels, plus `rendererVersion`), `insights` (+ratings), `themeId`, `characterId`, metadata. Renderers must remain backward compatible with older `rendererVersion`s. Archive mode reads only frozen data (+ the chapter's day/answer rows for journal browsing). Freeze **all** chart models and **all** insights with stable ids (`chartId`, `insightId`) so a future Storybook ([docs/v2-plan.md](v2-plan.md)) can select from them. Also store per-metric **chapter stats** in `FrozenChapter.stats` (n, mean, median, sd, min, max, fill rate): cheap, and it later powers chapter comparison, baselines and wrapped.

## 9. Import/export formats (all have `formatVersion`)
- **Form pack** `form-pack.json`: `{formatVersion, kind:'form-pack', aliases{}, libraries[], sections[], questions[{..., parts[]}]}` (`aliases` maps semantic names such as mood/sleepMinutes to metric keys, used by greetings); stable slug ids allowed (`q_studies`). Import modes: *merge* (skip existing ids, report conflicts) or *replace* (wipe form, keep answers only if ids match; warn).
- **Import UI (all import types):** one reusable Import dialog (modal) with a file picker (`<input type=file accept=.json,.zip>`) and a drag-and-drop zone. It detects the type from `kind`/manifest, validates against the versioned schema (clear errors, no partial writes), shows a preview (counts, conflicts) and a merge/replace choice before committing. Works fully offline (File API, no network). The bundled starter pack is only a sample shortcut through this same path; the app never depends on a specific pack.
- **Full backup zip (`formatVersion: 2`, `kind: 'full_backup'`)**: `manifest.json`, `form.json`, `chapters.json`, `days.json`, `answers.json`, `libraries.json`, `chapterAnswers.json`, `cycles.json`, `insights.json`, `baselines.json`, `stickers.json`, `settings.json` (excluding push tokens/VAPID secrets), `images/<chapterId>/*`, and `stickers/*`. Verified by dry-run re-read & validation before opening share sheet (`exportFullBackupZip`), and restored atomically (Replace or Merge) inside one Dexie transaction.
- **Safety snapshots (`trinqle_snapshots_db`)**: separate IndexedDB retaining up to 5 recent verified snapshots captured before Delete All, Import Replace, Chapter Close, and Data Health fixes.
- **Backup & chapter zips (`formatVersion: 1`)**: `manifest.json`, `chapter.json`, `days.json`, `answers.json`, `libraries.json`, `chapterAnswers.json`, `cycles.json`, `insights.json`, `stickers.json`, `images/*`. Verified before share; import checks zip-bomb limits (`2000` entries max, `25 MB`/entry, `100 MB` total inflated bytes, `50x` ratio), photo magic bytes, and `DOMPurify` SVG sticker sanitization.
- **CSV**: one wide daily table + a long table for sessions.
- Request `navigator.storage.persist()` automatically on first launch (`App.tsx`).

## 10. Notifications
Service worker handles `push` and `pushsubscriptionchange`, built with VitePWA `registerType: 'prompt'`. Server stores `{id, subscription, tz, prefs (incl. chapterPlannedEndDate), manageTokenHash, lastSent}` keyed by `sha256(endpoint)` in Upstash KV (failing with 503 if KV is unconfigured outside tests; using `SMEMBERS`+`MGET` pipeline and Lua atomic `recordSent`). Endpoints: `POST /api/subscribe` (issues 32-byte `manageToken` once), `/api/unsubscribe`, `/api/prefs`, `/api/send` (authenticated via `CRON_SECRET` for scheduler runs or `manageToken` for single-device test pushes, timing-safe comparison, strict HTTPS push-host allowlist, decoded `p256dh`/`auth` length checks, 4 KB body cap).

## 11. PWA
Manifest (name, icons, `display:standalone`, theme color from active theme), precache app shell, offline-first (`registerType: 'prompt'`). All 7 theme font families are bundled locally via `@fontsource/*` with zero external font network calls. Security headers (`Content-Security-Policy`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`) live in `vercel.json`.

## 11a. Greetings
`greetings.json` (code-owned, not editable in the app) is evaluated on Home load by `core/greetings`: build a context (built-in keys such as daysOfData, loggingStreak, missedYesterday, chapterDay, timeOfDay, formOpen, periodDay, plus values derived from the form pack's `aliases` over the last 3 days vs baseline); keep rules whose conditions all hold; take the highest priority tier; pick a line seeded by date + rule id. Rules whose alias is missing are skipped. Lines may include `{{key}}` tokens. No emojis.

## 11b. Search
Library: MiniSearch (or Fuse.js). One index, built in a Worker at start from IndexedDB and updated incrementally on every save/edit/import. Documents: each non-empty **text answer** (fields: text, questionId, partId, sectionId, date, chapterId), each **library item name** resolved through `AnswerLink` (indexed per day/question), day **title/one-liner**, chapter **title/summary**, **reflection** answers and custom prompts. Fuzzy (edit distance about 0.2 of term length, prefix match), case/diacritics-insensitive; quoted phrases do exact-phrase matching.
Filters (all combinable): source kind (text / library / day header / reflections), section, question, part kind, chapter, date range. Results grouped by day (newest first, toggle best match), each hit shows its source label (question, part) with highlight, and opens that day: editable if it belongs to the open chapter, read-only (archive mode) if closed. Covers **all chapters including the open one**. The Dashboard Journal view reuses the same index.

## 12. Theming
A theme owns **everything visual except layout**: colors, typography, shape (radius, button shapes), depth (shadows, borders), motion (easing, durations, entrance animations), **icon set** (nav, section, UI icons), sticker and chart styling, and component skins. Layout (placement and ordering of regions and elements) is fixed by the app and never theme-controlled.
Theme file: `{ id, name, tokens, iconSet, motion, components?: { Button, Card, Toggle, NavBar, ... skin overrides }, archive: { ... } }`. Components consume CSS variables and skin slots only. Adding a theme = one new file + one registry line; no data or logic change.
**Archive variant:** each theme defines how its monochrome archive look works (default: generated by desaturating accent and neutral colors while keeping the theme's own shapes, icons, depth and motion). It applies to every tab in archive mode **except Home, which stays full colour**. Chart series flagged `keepColor` keep their colours.

## 13. Character system
**Persona:** the character is always called **Piqsie** (setting `characterName`, default "Piqsie", pronounced "pixie") whatever SVG look is active; looks change, the name doesn't.

Characters are data: `characters/<id>/{character.svg, character.json}`. The **animation engine is written once** and shared by all characters. A character only declares what its parts are (roles) and optionally adds clips. No per-SVG code.

**Layers and roles.** Found by id convention or by explicit mapping in `character.json > roles`:
- single parts: `body head tail mouth`; pairs: `ear-left ear-right`, `eye-left eye-right`.
- **limbs: any number.** Names like `arm-left arm-right leg-left leg-right`, or `leg-1 ... leg-8`, or `limb-1 ... limb-N`. `roles.limbs` groups them: `{role:'leg', layers:[...], gait:'biped'|'quadruped'|'hexapod'|'octopod'|'custom', origin?}`.
- **Joints:** nest SVG groups (`leg-1 > leg-1-lower`); rotating a parent carries its children. Per-joint `swing` and `phase` can be set in json.
- Origins from `data-origin` on elements (or json). Missing roles are skipped; clips degrade (no limbs means walk becomes waddle/hop).

**Built-in clips (parameterised; same engine for every character):** idle: blink, breathe, tail-sway, ear-twitch, look-around. Actions: wave, bounce/jump (squash and stretch), spin, dance (sway + limb alternation + head bob), walk (translate across the stage + gait + body bob, flip with scaleX), sit, sleep (eyes closed, slow breathe, floating z), wiggle/purr, peek, shake. Gait patterns: biped (alternate), quadruped (diagonal pairs), hexapod (tripod), octopod (alternating tetrapods, for spiders), custom (phase offset per limb).
Per-character overrides of any clip parameter (`clips.walk.speed`, `amplitude`, ...). **Custom clips** are declarative keyframes in json, e.g. `{ "clips": { "flip": { "durationMs": 800, "targets": { "body": [ {"t":0,"rotate":0}, {"t":1,"rotate":360} ] } } } }`; no code.
**Views.** A character may have one or several views: `views: { front: { svg, roles, clips }, side: { svg, roles, clips } }` (more allowed, e.g. `sleeping`). Each clip declares the view it needs (walk uses `side`; idle, tap and greeting use `front`). The engine swaps views with a quick turn animation when the next clip needs a different one. Views share canvas size and ground line so swapping doesn't jump. A single-view character still works: front-only substitutes hop/waddle for walk; side-only walks but idles in profile. Single-view `character.json` may stay flat (implicit view `front`).

**Home stage behaviour:** a small scheduler picks random clips the character supports (weighted, mostly idle; sleepy when the form is locked or late). **Tap** plays a random clip from `reactions.tap`; rapid taps excite; long-press pets (purr). Other triggers: `saved`, `locked`, `chapterClosed`. Under `prefers-reduced-motion`: static pose plus a simple tap response.
Implementation: inline SVG, Web Animations API, `transform-box: fill-box`, one rAF loop only for walk translation.

**Import (phase 9):** file picker, sanitise (strip `<script>`, `foreignObject`, event handlers, external refs), auto-detect roles by id, then a **role-mapping screen** where unmapped layers can be tapped and assigned a role, saved as `character.json`.

## 14. Security and privacy
Data never leaves the device except user-initiated exports. Push server holds no journal data. Sanitise imported SVG and validate imported JSON/zip (size limits, schema, no path traversal).

## 15. Testing strategy
- Unit: logicalDay (tz, DST, window edges), effective-dating, metrics, each stat function, freeze/render round trip, import/export round trip.
- Property tests: form engine never produces zero for missing; chapter bounds 20 to 45.
- **Synthetic data + planted effects** (tools/): see plan.md Phase 7. Also a **pure-noise** dataset for false-positive control.
- E2E (Playwright, 390x844): first launch, quick/full night, backfill limits, chapter close, archive mode, export/import.
- Perf budgets: Home TTI < 1 s; analysis run <= 10 s on 6 months of dense data on a mid-range phone.
- A11y: axe checks per theme; contrast and touch targets.

## 16. Risks
Local-only data loss (mitigate: Back up now, weekly nudge, persistent storage). Chrome Web Speech is unreliable, so rely on Gboard voice typing. IndexedDB eviction. Statistical false positives on short chapters (mitigated by FDR, labels, deep windows). Scope creep (mitigated by phases in plan.md).
